The cleanest design was the wrong one

June 16, 2026 · 7 min read · iFood AI Platform

I almost shipped the textbook design. It was clean, push-based, and it would have made every team that adopted my platform a little more miserable. Here is why I threw it out, what I shipped instead, and the failure mode an agent-coding session caught that I had already waved off.

the setup

I work on MLGo! Gateway, a Go ML inference platform at iFood. It is not one service. It ships as a container image, and 10+ data science teams each deploy their own instance on AWS EKS, usually several pods behind a load balancer. The gateway sits in front of a team's already-served SageMaker endpoint and runs everything around the call: per-request enrichment, schema validation, the model invocation.

One feature: a team can promote a new DAG version as the default for a DAG name. The catch is how that promote lands. It is a single POST, so it hits exactly one pod. Every other pod in that deployment is now serving the old default until it finds out. They all have to converge, fast, without anyone restarting anything.

the design I almost shipped

The obvious answer is push. Put the change on a message bus, fan it out, every pod reacts in milliseconds. SQS, Kafka, Redis pub/sub. I have built that before and it works.

Then I remembered who deploys this thing. Not me. 10+ teams, each running their own instance, most of them data scientists who want to ship a model and not babysit a broker. A push design means every one of those teams has to provision the bus, get it approved, wire up the IAM, and operate it forever. I would be exporting my elegance as their ops cost, multiplied by every team that adopts the platform. That is the opposite of what a platform is supposed to do.

So I shipped the boring version. Pods poll a DynamoDB table (which every instance already depends on) for the current default, with an in-memory cache so the read is cheap and the steady state is quiet. A promote writes the new default; within one poll cycle every pod has it. No broker, nothing new for any team to run. Slightly less instant than push, completely invisible to the people adopting the platform.

the trap the agent caught

I had a working design and I was happy with it. Before calling it done I ran it through Claude Code as a red-team, asking it to break the thing under load. It kept pushing a case I had mentally filed under "won't happen": a cold start at scale.

Horizontal autoscaling does not bring pods up gently. A traffic spike spins up 200 pods, and something like 70% of them initialize in the same instant. Every one of them does its first read against the same single item, on the same partition key, at the same time. A single refresh shard plus a 60-second poll turns startup into a thundering herd straight onto one DynamoDB partition. Hot partition, throttling, exactly when you are trying to scale up.

I had waved this off because steady-state polling is trivial. The agent did not care about steady state. It cared about the worst second of the day, which is the second that pages you.

The fix was small. The same sync value gets written to 8 read shards. Each pod reads from a randomly chosen shard, and I added jitter to the startup poll so the 200 pods do not line up on the same tick. The herd spreads across partitions and across time. Same boring polling design, now it survives the worst second.

what I actually took from it

Two things.

First, perfect is contextual. The push design was better in a vacuum and worse in mine. The constraint that actually slowed the org down was not propagation latency, it was per-team infra. Optimizing for the wrong constraint gives you a clean design nobody wants to adopt. I now ask "who pays for this, and how many of them are there" before I ask "what is the elegant version".

Second, agents are good at the case you have already dismissed. I did not use Claude Code to write the sharding code. I used it to argue with me about the part I was sure about, and it found the 200-pod cold start I had filed under "won't happen". That is the part of agentic coding I actually rely on: not the typing, the adversarial second opinion on my own confidence.

The whole thing shipped in one two-week sprint. (Unrelated trivia: there is a separate write-sharding fix I did for a DynamoDB hot partition during dinner peak. Different incident, same lesson, also mine.)
