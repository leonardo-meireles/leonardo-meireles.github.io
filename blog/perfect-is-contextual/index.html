The cleanest design was the wrong one

June 16, 2026 · 7 min read · backend

I almost shipped the textbook design. It was clean, push-based, and it would have made every team that adopted my platform a little more miserable. Here is why I threw it out, what I shipped instead, and the failure mode an agent-coding session caught that I had already waved off. The details below are generalized on purpose, but the lesson is exactly as it happened.

the setup

The thing I work on is an internal platform that other teams self-deploy. It is not one shared service. It ships as a container image, and each team runs its own instance behind a load balancer, usually several pods. The platform sits in front of a model endpoint and does the work around the call: per-request enrichment, validation, the invocation.

One feature: a team can change which config version is the live default. The catch is how that change lands. It arrives as a single request, so it hits exactly one pod. Every other pod in that deployment is still serving the old default until it finds out. They all have to converge, fast, without anyone restarting anything.

the design I almost shipped

The obvious answer is push. Put the change on a message bus, fan it out, every pod reacts in milliseconds. SQS, Kafka, Redis pub/sub. I have built that before and it works.

Then I remembered who deploys this thing. Not me. A lot of teams, each running their own instance, most of them not interested in babysitting a broker. A push design means every one of those teams has to provision the bus, get it approved, wire up the access, and operate it forever. I would be exporting my elegance as their ops cost, multiplied by every team that adopts the platform. That is the opposite of what a platform is supposed to do.

So I shipped the boring version. Pods poll a key-value store they already depend on for the current default, with an in-memory cache so the read is cheap and the steady state is quiet. A change writes the new default; within one poll cycle every pod has it. No broker, nothing new for any team to run. Slightly less instant than push, completely invisible to the people adopting the platform.

the trap the agent caught

I had a working design and I was happy with it. Before calling it done I ran it through Claude Code as a red-team, asking it to break the thing under load. It kept pushing a case I had mentally filed under "won't happen": a cold start at scale.

Autoscaling does not bring pods up gently. A traffic spike spins up a lot of pods at once, and a big chunk of them initialize in the same instant. Every one of them does its first read against the same key, on the same partition, at the same time. A single refresh shard plus a poll on the order of a minute turns startup into a thundering herd onto one partition. Hot partition, throttling, exactly when you are trying to scale up.

I had waved this off because steady-state polling is trivial. The agent did not care about steady state. It cared about the worst second of the day, which is the second that pages you.

The fix was small. The same value gets written to a handful of read shards. Each pod reads from a randomly chosen shard, and I added jitter to the startup poll so the pods do not line up on the same tick. The herd spreads across partitions and across time. Same boring polling design, now it survives the worst second.

what I actually took from it

Two things.

First, perfect is contextual. The push design was better in a vacuum and worse in mine. The constraint that actually slowed the org down was not propagation latency, it was per-team infra. Optimizing for the wrong constraint gives you a clean design nobody wants to adopt. I now ask "who pays for this, and how many of them are there" before I ask "what is the elegant version".

Second, agents are good at the case you have already dismissed. I did not use Claude Code to write the sharding code. I used it to argue with me about the part I was sure about, and it found the cold-start stampede I had filed under "won't happen". That is the part of agentic coding I actually rely on: not the typing, the adversarial second opinion on my own confidence.
